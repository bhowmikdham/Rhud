# Rhud Architecture Debug Sweep — Confirmed Findings

> Generated by a multi-agent debug swarm (22 finder agents → adversarial verification → synthesis),
> across two sweeps. **Part 1** (below) = the 7 finders verified on the first run. **Part 2** (appended
> at the end) = the other 15, re-run with free-text verification after the structured-output tool failed.
> Branch: `ux-journey-fixes`. ~290 agents total, ~6.7M tokens. **110 adversarially-confirmed findings**
> (≈108 distinct — the reviewer line-item drop and the audit-chain boundary were each independently
> confirmed twice). All 22 finder areas are now covered; `pnpm typecheck` is clean across api/web/shared
> (strict + `exactOptionalPropertyTypes` on).

## Severity rollup (all confirmed, both sweeps)

| Severity | Count | Headliners |
|----------|-------|-----------|
| **Critical** | 3 | tenant-isolation-1 (RLS silently off if `APP_DATABASE_URL` unset), site-enum-1 (SSRF → EC2 creds), ml-bridge-1 (constant predictions) |
| **High** | ~35 | RLS FORCE gap, quote-approve VP/CEO bypass, reviewer line-items dropped, no JWT revocation, email-verify bypass, no rate limiting, 4× unguarded concurrent pipelines, audit-chain event drop, Odoo won/lost not synced, … |
| **Medium** | ~45 | validation/500 gaps, IDOR on file routes, schema↔migration drift, web stale-state races, template publish bypass, gamma URL → iframe/email, … |
| **Low** | ~26 | various hardening / efficiency / UX-correctness items |

**The 3 criticals:**
1. **tenant-isolation-1** — `APP_DATABASE_URL` is optional and silently falls back to the BYPASSRLS superuser `DATABASE_URL`; one missing/typo'd env var disables RLS entirely while the boot log still says "RLS enforced" → **full cross-tenant data exposure**. (Compounded by tenant-isolation-2: `FORCE ROW LEVEL SECURITY` on only 8 of ~38 tables.)
2. **site-enum-1** — SSRF in the crawler → any rep can read EC2 instance metadata and steal the IAM role credentials.
3. **ml-bridge-1** — predict/train feature-space mismatch → trained tenants get a constant price regardless of scope.

> finders produced confirmed output. Part 2 re-ran the other 15 finders with free-text verification
> (no structured-output dependency) and recovered 62 more confirmed findings.

## Architectural themes (systemic, not one-offs)

1. **Multi-step operations are not atomic — "read-then-write without a lock" recurs everywhere.**
   `predict` spans 3 separate transactions (pricing-quotes-4); Odoo push does cross-service writes
   with no rollback and can create duplicate leads (odoo-3); site-enum can double-fire a crawl
   (site-enum-7); approval-threshold gate is a TOCTOU (pricing-quotes-8); invite accept races to a
   raw P2002 500 (auth-5). The fix pattern is the same: claim/guard rows atomically
   (`updateMany where status in (...)`) or `SELECT … FOR UPDATE`.

2. **State-machine guards are applied inconsistently.** `reject()`, `revertApproval()`, and
   reviewer-hold all check the engagement's current status — but `approve()` does not, so a
   rejected/sent/closed deal can be silently re-approved and re-fire Odoo "won" sync
   (pricing-quotes-1). `publish()` likewise guards the wrong scope (pricing-ratecards-1).

3. **The ML pricing pipeline is silently wrong for trained tenants.** Predict-time features are
   keyed by per-tenant node UUIDs that can never match the training feature space, so the model
   sees an all-zero vector and returns a constant (ml-bridge-1, **critical**); and reported
   accuracy is in-sample leakage, so the confidence number is meaningless (ml-bridge-4). The
   "adaptive intelligence" is effectively a constant for any non-cold-start tenant.

4. **The auth/session model is incomplete as a security control.** No JWT/session revocation —
   demote/delete/password-reset don't evict an existing token for up to 24h (auth-2);
   email-verification is bypassable via magic-link or reset (auth-1); no rate limiting anywhere on
   auth/public endpoints (auth-3); the bounded token-candidate scan can drop a valid token under
   load (auth-4).

5. **Untrusted input reaches business logic without validation.** SSRF in the crawler (site-enum-1,
   **critical**); raw `matrix` endpoints `.trim()`/`.map()` non-string cells into 500s
   (pricing-ratecards-4, llm-4); unbounded tech-adjust price (pricing-quotes-7); device fingerprint
   built from attacker-controlled headers (site-enum-2).

6. **The LLM layer lacks production hardening.** Budget is advertised but never enforced
   (llm-1); request timeout doesn't cover the body read (llm-2); truncated output is never detected
   and silently corrupts parsed rate cards (llm-3); Anthropic (the default provider) has no retry
   (llm-5); raw upstream error bodies are forwarded to clients (llm-6).

7. **Odoo two-way sync is not wired for autonomous operation.** Inbound webhooks are stored but
   never processed without a manual admin click (odoo-1); unlink destroys promoted audit rows and
   orphans engagements (odoo-2); echo-suppression compares mismatched clocks (odoo-4); the poll
   cursor drops leads created in the same second (odoo-5).

8. **Pricing/quote math diverges from what the UI shows.** Reviewer-entered line items
   (travel/discount) are dropped from the approved price (pricing-quotes-2); the JS crawler marks
   every site an SPA and overprices CMS pages (site-enum-4); `parseRupees` imports formula text as a
   flat price (pricing-ratecards-5); null-methodology tiers can shadow the correct tier
   (pricing-ratecards-6).

## Full findings by subsystem

### pricing — rate cards

- **[high] pricing-ratecards-1** `pricing.service.ts:172` — `publish()` tier-count guard counts **all tenant tiers**, not the card's, so an empty card is publishable if any other card has tiers → all-unmatched quotes. Fix: scope count to `serviceLine.rateCardId = id`.
- **[high] pricing-ratecards-2** `dto.ts:87` — `CreateRateCardDto` omits all inference-ontology fields; the ValidationPipe whitelist strips them, so `POST /rate-cards` silently drops `inferenceContext`/hints. Fix: add `@IsOptional()` fields.
- **[high] pricing-ratecards-3** `rate-card.parser.ts:104` — parser can emit duplicate service-line slugs → Prisma P2002 → uncaught 500 that aborts the whole import. Fix: dedupe slugs or catch P2002. (`splitDeviceLine` has the same risk.)
- **[med] pricing-ratecards-4** `pricing.controller.ts:115` — `/rate-cards/parse` has no DTO; non-string matrix cells hit `.trim()` → 500. Fix: `ParseMatrixDto` or coerce with `String()`.
- **[med] pricing-ratecards-5** `rate-card.parser.ts:287` — `parseRupees` takes the leading integer of free-text/formula cells (e.g. `"40000 upto next 99K LOC"`) ×100 and persists it as a flat price, no warning → silent pricing corruption.
- **[med] pricing-ratecards-6** `packages/shared/src/pricing.ts:343` — `pickTier` treats null methodology as a wildcard and returns first match; a null tier can shadow the correct typed tier, and `findOverlappingTiers` buckets null separately so the publish validator misses it.
- **[med] pricing-ratecards-7** `pricing.service.ts:101` — `create()` never sets `version` (defaults 1); re-importing a card with the same name violates `@@unique([tenantId,name,version])` → uncaught 500. Fix: auto-increment version or catch P2002 → 409.
- **[low] pricing-ratecards-8** `pricing.service.ts:145` — open-priced services created via API all get `position=0`; `loadFull` sorts by position → non-deterministic ordering vs the fixture path.

### pricing — quotes & predictions

- **[high] pricing-quotes-1** `prediction.controller.ts:233` — `approve()` overwrites status/price from **any** source state (no guard, unlike reject/revert/hold). Re-approves terminal deals, re-fires Odoo sync, races on double-click.
- **[high] pricing-quotes-2** `prediction.controller.ts:243` — approved price is derived purely from the Prediction row; reviewer-added line items (travel/tools/**discounts**) folded into `grandTotalCents` are never read → wrong customer price.
- **[med] pricing-quotes-3** `quote.service.ts:363` — enrichment `.map()`s raw `baseBreakdown` JSON unconditionally; a non-array legacy row → TypeError → the whole approval-card read 500s. Also adds a rate-card load on every poll. Fix: `Array.isArray` guard.
- **[med] pricing-quotes-4** `prediction.service.ts:73` — predict spans 3 separate transactions with no lock; concurrent re-predicts interleave and can pin the wrong snapshot / orphan a prediction from its quote.
- **[med] pricing-quotes-5** `quote.service.ts:332` — mirror write of `engagement.predictedPriceCents` is gated on `totalCents>0`, so a legitimate drop to 0 leaves a stale non-zero mirror that disagrees with the quote row.
- **[low] pricing-quotes-6** `prediction.controller.ts:247` — in `cold_start` regime `bandPct=0` so `bandLowCents===predictedPriceCents`; the "aggressive" approval choice is silently identical to "recommended".
- **[low] pricing-quotes-7** `prediction.controller.ts:106` — `TechAdjustDto` validates only `@Min(0)`, no upper bound or relation to base; combined with quotes-1 a fat-fingered price one-clicks to approval.
- **[low] pricing-quotes-8** `prediction.controller.ts:279` — VP/CEO approval thresholds are read in a separate transaction from the status write → TOCTOU; a racing threshold change lets a large deal bypass the gate.

### llm

### site-enum & gathering

- **[critical] site-enum-1** `crawler.service.ts:161` — **SSRF**: `isPlausibleUrl` only checks scheme+dot; no loopback/link-local/RFC1918 blocklist, redirects followed. Reps can read cloud metadata / internal services; crawl body is persisted and returned. Fix: resolve host, reject private IPs, re-check every redirect hop, apply to JS crawler + robots/sitemap fetches too.
- **[high] site-enum-2** `gathering.controller.ts:89` — device-fingerprint binding is built from attacker-controlled `X-Forwarded-For`/UA/Accept-Language; a stolen token is replayable by spoofing one header. Fix: `trust proxy` + use `req.ip`; treat IP as advisory.

- **[med] site-enum-6** `site-enum.service.ts:456` — classify writes via `updateMany(where url)`; same-url endpoints all get the last classification processed (order-dependent), and `classifiedUrls` is inflated.
- **[med] site-enum-7** `site-enum.service.ts:353` — `runEnumeration` only guards `crawling`/`classifying`; `pending`/`retry_queued` rows aren't claimed atomically, so kickoff + retry + cron sweep can double-fire a crawl. Fix: atomic `updateMany` claim.

## extraction — extraction & email  (3 confirmed)

### extraction-1 — Email-extraction cache is keyed without the signed-in user, returning another user's forwarder-disambiguation result
- **Severity:** high
- **File:** `apps/api/src/email-extractor/email-extractor.service.ts:128-138` (lookup), `319` / `341` (cache key); uniq at `apps/api/prisma/schema.prisma:370`
- **Evidence:** `const cached = await this.readCache(tenantId, dto.messageId); if (cached) return cached;` keyed only on `where: { email_extraction_tenant_message_uniq: { tenantId, messageId } }`, while the result is computed from `tenantUserEmail` — injected into the LLM prompt at line 191 (`Signed-in Rhud user (internal — NOT the client): ${tenantUserEmail}`) and used by `disambiguateForwardedSender` (email-parser.ts:57-64) to decide who is the internal forwarder.
- **Impact:** The whole point of `tenantUserEmail` is forwarder disambiguation: which party is INTERNAL is computed against the signed-in user's domain. Schema confirms a tenant can hold users with different email domains (only `@@unique([email])` global; no per-tenant domain constraint — schema.prisma:888). User A (`alice@vendor.com`) previews messageId X; the result is cached under `(tenant, X)` with disambiguation relative to `vendor.com`. User B (`bob@partner.com`, same tenant) opens the same messageId and is served A's result — internal/external party attribution computed against the wrong domain, so `isForwarded`/`forwardedFrom`/client-vs-partner resolution can be wrong for B.
- **Fix:** Add `tenantUserEmail` (or its lowercased domain — the disambiguation only depends on the domain) to the cache key / unique index, treating a mismatch as a miss; or only cache the `tenantUserEmail`-independent portion.
- **Verdict:** confirmed — `readCache`/`writeCache` key only on `(tenantId, messageId)` (lines 319, 341) yet `runLlm` and the heuristic both branch on `tenantUserEmail`; schema permits mixed-domain users per tenant.

### extraction-2 — Switching/reconfiguring the LLM provider does not invalidate cached email extractions
- **Severity:** medium
- **File:** `apps/api/src/email-extractor/email-extractor.service.ts:82, 128-130, 316-329`
- **Evidence:** `const EXTRACTOR_VERSION = 2;` and in `readCache`: `const wrapped = row.payload as ... { v?: number; result?: ... }; if (wrapped?.v !== EXTRACTOR_VERSION || !wrapped.result) return null; return wrapped.result;`. The schema stores `model` (schema.prisma:367) and `writeCache` persists it (line 342-343), but `readCache` only `select: { payload: true }` and never reads `model`. Invalidation is purely on the hard-coded version.
- **Impact:** The cache short-circuits at line 129-130 before `getProviderName` (line 134) is ever consulted, so a tenant that switches LLM providers/models (or fixes a bad model name/key) keeps serving the old provider's cached extraction for any previously-previewed messageId for up to `CACHE_TTL_DAYS = 30`. No way to force a refresh from this endpoint short of bumping `EXTRACTOR_VERSION` globally (which nukes all tenants' caches).
- **Fix:** Store the active provider+model in the payload wrapper and treat a mismatch as a miss (same as the version check), or include model in the key. The `model` column is already populated and available.
- **Verdict:** confirmed — `readCache` selects only `payload` and validates only `wrapped.v` against the constant; the persisted `model` is never used for invalidation.

### extraction-4 — Concurrent file extractions on one engagement can lose auto-promoted answers (non-atomic read-then-create)
- **Severity:** medium
- **File:** `apps/api/src/extraction/extraction.service.ts:1551-1574` (race); kickoff at `318`, `347-349`; unique key at `apps/api/prisma/schema.prisma:495`
- **Evidence:** `kickoffForEngagement` loops `await this.kickoff(...)`, but `kickoff` fires extraction without awaiting it: `void this.runExtraction(tenantId, fileId).catch(...)` (line 318). So per-file `runExtraction` → `persistResult` → `promoteAnswersFromPoints` (line 1231) run concurrently. Inside, `existingAnswers = await db.engagementAnswer.findMany(...)` then `await db.engagementAnswer.create(...)` with no upsert, guarded only by the in-process `alreadyAnswered` set. The unique key is `@@unique([engagementId, nodeId, iterationIndex], map: "engagement_answers_eng_node_iter_key")`.
- **Impact:** Two files extracting a value for the same top-level node both read an empty `existingAnswers`, both `create` `(eng, node, 0)`; the second throws a unique violation that is caught and logged (`auto-promote answer failed`, line 1590). Not a crash, but which file's value lands is non-deterministic across concurrency/re-runs, and a genuinely better value from the losing file is silently dropped rather than reconciled.
- **Fix:** Use `upsert` on the unique key (or `createMany({ skipDuplicates: true })`) so the operation is atomic and deterministic, removing the swallowed unique-violation; if "form answer wins" must hold, still gate on absence via conflict-do-nothing.
- **Verdict:** confirmed — fire-and-forget `runExtraction` (line 318) lets multiple `promoteAnswersFromPoints` run concurrently; the read-then-`create` (1551/1566) is not atomic and the catch (1589) swallows the unique violation.


## outlook — integrations: outlook + add-in  (5 confirmed)

### outlook-1 — Rep's scope-field edits and "ask the client" selections are silently discarded on create
- **Severity:** high
- **File:** apps/outlook-addin/src/App.tsx:228-239 (and apps/outlook-addin/src/lib/api.ts:75-94, apps/api/src/engagements/dto.ts:74-140)
- **Evidence:** `handleCreate` posts only identity fields — `createOpportunity(auth.token, { msg, fromEmail: clientEmail, ..., partnerRole })` — and `createOpportunity` serializes only `fromEmail/fromName/clientNameOverride/contactPhone/clientAddress/partner*/subject/bodyText/messageId/source`. Neither the reviewed `fields` (`updateField`/`markNA`/`status`) nor the `askClient` set is sent. `CreateOpportunityFromEmailIngestDto` has no field for structured scope or an ask-client list. The controller routes to `this.ingestion.receiveAndPromote(...)`, which `receive`s an `email` artifact then `promote`s it and fires `void this.extraction.kickoffForEngagement(...)` (ingestion.service.ts:401), so the server re-extracts the raw body. The `overrides` object only carries client/partner *identity* (PromoteArgs.overrides, ingestion.service.ts:102-114) — not the field grid.
- **Impact:** Everything the rep does in the Review step (correcting mis-extractions, marking rows N/A, queueing fields for the client) is thrown away. The opportunity is built purely from a fresh server-side extraction of the same email. ### web-rest-1 — `gFetch` error path reads the response body twice ("body already used")
- **Severity:** medium
- **File:** apps/web/src/lib/api.ts:1988-1991
